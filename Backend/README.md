# Customer Segmentation Backend

A FastAPI backend that stores customer transactions, calculates RFM (Recency, Frequency, and Monetary) features, predicts a customer segment with a trained K-Means model, and exposes the results for a dashboard or frontend application.

## What This Project Does

When a transaction is submitted, the backend:

1. Creates the customer record if it does not already exist.
2. Saves the transaction in PostgreSQL.
3. Calculates the customer's RFM values from all of their transactions.
4. Uses the saved machine-learning pipeline to assign a segment.
5. Stores the latest RFM values and prediction in `customer_rfm`.
6. Returns the segment and RFM values as JSON.

The trained segmentation model uses three features:

- **Recency**: number of days since the customer's most recent purchase, relative to the dataset reference date.
- **Frequency**: number of distinct invoices for the customer.
- **Monetary**: sum of `quantity * unit_price` across the customer's transactions.

The model has three K-Means clusters, mapped to these names:

| Cluster | Segment |
| ---: | --- |
| 0 | At-Risk / Hibernating |
| 1 | Potential Loyalists |
| 2 | Champions / VIP |

> Cluster labels are generated by K-Means and are not guaranteed to keep the same meaning after retraining. The `CLUSTER_NAMES` mapping in `scripts/predections.py` should be reviewed whenever the model is retrained.

## Requirements

- Python 3.10 or newer
- PostgreSQL running locally or on a reachable host
- A PostgreSQL database containing the tables described below
- The saved model at `ml/CUSTOMER_SEGMENTAION_MODEL.pkl`
- The Excel training dataset if the model must be retrained

The code imports SQLAlchemy and the PostgreSQL driver. If they are not already installed in the environment, install them with:

```powershell
pip install sqlalchemy psycopg2-binary
```

## Installation

From the `Backend` directory:

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install -r requirements.txt
pip install sqlalchemy psycopg2-binary
```

On macOS/Linux, activate the environment with:

```bash
source venv/bin/activate
```

Create a `.env` file in the project root. The current project uses the following values:

```env
PROJECT_ROOT=E:/path/to/Customer Segmentation/Backend
DATASET_NAME=ml/Online Retail.xlsx
MODEL_DIR=ml
LOG_DIR=logs
MODEL_NAME=CUSTOMER_SEGMENTAION_MODEL.pkl
LOG_NAME=app.log
RANDOM_STATE=42

DB_HOST=localhost
DB_PORT=5432
DB_NAME=CustomersInfo
DB_USER=postgres
DB_PASSWORD=your_password
```

`PROJECT_ROOT` must point to this backend directory. `MODEL_NAME`, `MODEL_DIR`, `LOG_DIR`, and `LOG_NAME` are used by both the training and prediction scripts.

Do not commit a real `.env` file or database password to source control.

## Database

The application expects PostgreSQL tables with at least these columns:

```sql
CREATE TABLE customers (
    customer_id INTEGER PRIMARY KEY
);

CREATE TABLE customer_transactions (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
    invoice_no VARCHAR(100) NOT NULL,
    invoice_date DATE NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC NOT NULL
);

CREATE TABLE customer_rfm (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER PRIMARY KEY REFERENCES customers(customer_id),
    recency INTEGER NOT NULL,
    frequency INTEGER NOT NULL,
    monetary NUMERIC NOT NULL,
    cluster_id INTEGER NOT NULL,
    segment VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

The application does not create tables automatically. Create the database and tables before starting the API.

## Running the API

Start the development server from the project root:

```powershell
uvicorn app.main:app --reload
```

The API is available at:

- `http://127.0.0.1:8000`
- Swagger UI: `http://127.0.0.1:8000/docs`
- ReDoc: `http://127.0.0.1:8000/redoc`

The frontend origins currently allowed by CORS are `http://localhost:5173` and `http://localhost:5174`.

## API Endpoints

### Add a transaction and predict a segment

```http
POST /predection
Content-Type: application/json
```

Request body:

```json
{
  "customer_id": 12345,
  "invoice_no": "536365",
  "invoice_date": "2010-12-01",
  "quantity": 6,
  "unit_price": 2.55
}
```

Example response:

```json
{
  "customer_id": 12345,
  "recency": 1,
  "frequency": 1,
  "monetary": 15.3,
  "cluster_id": 1,
  "segment": "Potential Loyalists"
}
```

The endpoint is spelled `/predection` in the current code and must be called with that spelling.

### List all transactions

```http
GET /transactions
```

Returns `count` and a `transactions` array ordered by newest invoice date.

### List one customer's transactions

```http
GET /transactions/{customer_id}
```

Returns only transactions for the requested customer.

### List all RFM predictions

```http
GET /rfm
```

Returns `count` and an `rfm` array containing the latest stored RFM and segment record for each customer.

### Get one customer's RFM prediction

```http
GET /rfm/{customer_id}
```

Returns the customer's stored RFM record. Returns `404` when no record exists.

### Get dashboard totals

```http
GET /dashboard
```

Returns the total number of RFM records and counts for the segment names used by the dashboard query.

## Model Training

`scripts/training.py` trains the segmentation model from `DATASET_NAME`:

```powershell
python -m scripts.training
```

The training process:

1. Reads the Online Retail Excel file.
2. Removes duplicate rows and cancelled invoices.
3. Removes records without `CustomerID`.
4. Builds customer-level RFM features.
5. Applies `QuantileTransformer`.
6. Trains a three-cluster K-Means pipeline.
7. Calculates silhouette, Davies-Bouldin, and Calinski-Harabasz metrics.
8. Saves the model to `MODEL_DIR/MODEL_NAME`.
9. Saves metrics to `ml/metrics.json`.

Retraining overwrites the existing model file. Restart the API after retraining so the newly saved model is loaded into memory.

## Optional Churn Model

The prediction script also looks for:

```text
ml/churn_model.joblib
```

If that file exists, the API prediction includes `churn_probability` and `churn_prediction`. There is currently no churn-training script in this repository, so segmentation works without it.

## Testing the Database Connection

Run the database smoke test with:

It attempts to connect to PostgreSQL and prints the number of rows in `customer_transactions`.

## Logging

Prediction and application messages are written to `logs/app.log` and also emitted to the console. The log directory is created automatically when the prediction module loads.

## Important Current Limitations

- The `Transaction` schema currently declares `customer_id` as required, even though the route contains logic for a missing customer ID. Automatic ID generation therefore requires changing the schema to make `customer_id` optional.
- Database tables and migrations are not included; they must be created separately.
- There is no automated test suite yet. `test.py` is a database connectivity smoke test, not an API test.
- The API currently returns raw exception messages with HTTP 500 responses. Production deployments should use safer error messages and structured logging.
- RFM values are calculated from the database transaction history, while training uses the Excel dataset. These sources should use compatible definitions and data quality rules.
- The dashboard query uses segment names such as `Loyal Customer` and `Potential Customer`, while the prediction mapping currently returns `Potential Loyalists` and `Champions / VIP`. Those names should be aligned for dashboard counts to be accurate.
